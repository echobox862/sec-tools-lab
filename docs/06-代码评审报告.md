## 二、问题清单

### 严重

无。上一轮审计的高危项 H1（无界线程）已随重构修复。

### 中等

**Med-1 校准闸门与需求分析接口不一致**
位置：`web-login-bruter/web_bruter.py` 的 `brute()`（L190-198）；需求定义见 `docs/04` 接口节。
原因：docs/04 定义的 `calibrate(session, form, username, right_pwd, wrong_pwd)` 要求用一真一假两个密码验证 marker 可区分；实现只提交一次错误密码（`__calibrate_wrong_pwd__`），验证的是请求链路可用，没有验证「真密码会被判成 success」。爆破前也确实拿不到真密码，所以这个偏差有客观原因，但后果是：如果 fail_marker 恰好同时出现在成功页上，工具会把命中判成 fail，且校准阶段发现不了。
影响：漏报（把命中当失败继续跑），报告不会提示。
建议：校准阶段无法验证真侧，就把 docs/04 的接口描述改成与实现一致（链路校验），并在 README 提醒用户用 `--success-marker` 显式指定成功特征；或者实现「假密码 + 检查响应中 fail_marker 不出现在疑似成功位置」的弱校验。二选一，当前文档与代码各说各话最差。

**Med-2 字典一次性载入内存**
位置：`ssh-bruter/ssh_bruter.py` 的 `load_wordlist()`、`web-login-bruter/web_bruter.py` 的 `main()`。
原因：shared/wordlist.py 用列表一次性读入。上亿行字典会占 GB 级内存，与 02 工具「生成器流式输出」的设计矛盾。上轮已消除 `words[:max_attempts]` 的切片复制，但载入本身仍是全量。
建议：完全流式化需要先解决 `attempts_planned` 统计依赖 `len(words)` 的问题（报告字段语义要改），属于公开行为变更。短期在 docstring 与 README 标注字典规模上限建议（百万行以内）；长期改造时同步调整报告字段。

**Med-3 ssh_bruter 的并发正确性没有并发测试**
位置：`tests/test_ssh_bruter.py`。
原因：所有 brute 流程测试都用 `threads=1`。线程锁（results_lock）、乱序完成下 `tried = len(timeline)` 的正确性、stop event 的竞态，这些恰恰是多线程代码最容易出错的部分，目前只有串行路径被验证过。
影响：重构引入的线程模型缺陷（如果有的话）测试抓不到。
建议：补一个 `threads=5`、50 词、对关闭端口的用例，断言 `tried == 50`、timeline 无重复序号、无异常退出。这条不需要真实 SSH 服务。

**Med-4 verify.py 不区分「注入点不可用」与「tamper 破坏语义」**
位置：`sqlmap-tamper/verify.py` 的 `check_semantics()`。
原因：当 raw 基线的长度差为 0（注入点本身不可用，比如靶场没启动对应关卡），所有变体的 `db_accepts` 都会判 False，输出里 tamper 全部 FAIL。用户会误以为 tamper 有问题，实际是基线没建立。
影响：误导排查方向。
建议：`baseline == 0` 时提前输出「raw 基线无差异，请先确认注入点可用（建议跑 Less-8 的 and 1=1 / 1=2 手工验证）」并跳过变体判定，而不是给出 FAIL。

### 轻微

**Min-1 死 import**
位置：`ssh-bruter/ssh_bruter.py` L15-16、`web-login-bruter/web_bruter.py` L16-17。
原因：export 收敛到 shared/report_io 后，`csv`、`json` 两个 import 不再被使用（已用 grep 确认零调用）。
建议：删除这两行。

**Min-2 无效断言（测试写了等于没写）**
位置：`tests/test_ssh_bruter.py` L99；`tests/test_scanner.py` L192-196。
原因：L99 的 `assertEqual(words, A if words != B else B)` 无论实际值是什么都会通过；L192 的测试在环境不满足条件时整个断言分支不执行，属于空转。测试套件里只有这两处。
建议：L99 明确预期行为（当前实现保留行内空白，断言 `["  abc  "]` 并把 docstring 改成「记录实际行为：仅剥离行尾换行」）；L192 要么造出确定的全 filtered 场景（不可路由地址 + 短超时已接近，可收紧），要么删掉该用例。

**Min-3 预检使用空用户名**
位置：`ssh-bruter/ssh_bruter.py` L59（`transport.auth_none("")`）。
原因：预检用空用户名，与实际爆破的 username 不一致；部分 sshd 对空用户名直接断开，预检会误报「目标不可用」。
建议：`detect_auth_methods` 增加 username 参数，main 里传入 `args.username`。

**Min-4 seps 空段处理与其他参数不一致**
位置：`dict-generator/dicgen.py` L143。
原因：`--seps 'a,,b'` 的空段被静默当作「直连」接受，而 years/tails 对空段直接报错。
建议：统一拒绝空段；需要「直连」语义时用文档说明的默认值（不传 --seps）。

**Min-5 conn_error 复用 redirect 字段**
位置：`web-login-bruter/web_bruter.py` 的 `attempt()` 与 `brute()` L196。
原因：连接失败时异常消息存在 AttemptResult.redirect 槽位里，brute 打印 `res.redirect` 展示错误。字段语义混用，读代码容易误会。
建议：AttemptResult 增加 error 字段，redirect 只放重定向地址。

**Min-6 docs/00 的目录结构已过时**
位置：`docs/00-需求分析总览.md` 第四节。
原因：写的是规划稿（根目录名「安全工具/」、「common/ 暂不抽」），实际已落地为 sec-tools-lab + shared/。
建议：同步更新，避免新读者按旧结构找文件。

## 三、测试覆盖评估

做得好的：126 个用例全绿；mock 服务覆盖了 04 的完整链路（含一次性 token 的证据性测试）；tamper 的语义等价验证用了可精确断言的 mock 靶场；paramiko 缺失时自动 skip 而不是报错。

覆盖缺口（按影响排序）：
1. 并发路径零覆盖（见 Med-3）。
2. `brute()` 的 unknown_marker 终止路径没有直接测试（judge 层测了 unknown，终止逻辑没测）。
3. scanner 的 KeyboardInterrupt 分支没有测试（partial report 行为未验证）。
4. verify 的 `--output` 分支未测。

断言有效性：整体扎实，2 处无效断言见 Min-2。没有发现「断言写反」「捕获异常后跳过断言」的情况。

## 四、安全评估

上一轮审计的安全结论在本轮复核中维持：CLI 参数属于可信操作者输入；远端响应作为不可信输入的所有消费点（HTMLParser、headers、decode）处理安全；无命令拼接；报告已脱敏；AutoAddPolicy 与 --insecure 的风险均有文档声明。本轮重构新增的 shared 模块与 sys.path 引导不引入新的信任边界问题（本地脚本加载本地模块）。

无严重/中等安全问题。两点说明：`verify.py --tamper` 会执行任意本地 Python 文件，等同运行本地代码，README 已警示不要加载不可信来源；四个工具的 `-o` 输出路径可覆盖任意可写文件，这是命令行工具的固有语义，不是缺陷。

## 五、建议的处理顺序

Med-1（文档与实现二选一对齐）和 Med-3（补并发测试）成本最低、收益直接，建议先做；Med-4 是十行以内的改动；Med-2 需要决策报告字段语义，可以放最后。轻微项顺手清理即可，Min-2 的无效断言建议在补 Med-3 测试时一并处理。
